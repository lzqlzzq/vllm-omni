# 单阶段与 KV transfer 两阶段：架构 probe

本轮按用户要求定位两条链路的差异，保留两阶段设计及上游采样、NAR 融合/编译/velocity Graph、VAE。只新增外置观察脚本和报告，生产源码与 [按需分配版本](../2026-10-03-yue2-kv-on-demand/README.md) 的 12 项快照哈希完全相同，未 commit/push。

当前证据支持继续保留两阶段实验。它消除了真实存在的 HOLD backbone 工作，也确实提前完成了整批 semantic；本轮并发差距主要表现为声学执行变长及后段排队。KV gather 的复制成本很小，IPC 释放及同步 ACK 则有可见停顿。尚未通过干预实验将声学变化唯一归因于 CUDA context、stream priority 或某项调度策略。

## 方法与可比范围

- 同一 RTX 3090，同卡运行；torch 2.13/cu130、vLLM 0.30、transformers 5.14。源码 HEAD `631f5573` 加当前未提交两阶段实验；源码哈希见 [source-sha256.json](source-sha256.json)。
- 相同四条 prompt/seed，固定输出 **512/768/1024/1280 帧**，总音频 **143.354667 秒**。以 `yue2_min_tokens` 配合最大帧数固定工作量，均为预算结束、`truncated=1`，**不是自然 EOS 测试**。
- 固定的是长度和计算形状，不是相同 semantic token。probe 中第 1 首 token 全同，另三首首次分叉的零基位置为 536、611、542。不得作为 token/audio parity 验收；条件 prefill 的数值路径也不同。
- 主模型 revision `c044757a011169583f363168348ae380946efff8`，VAE revision `152733a19ad43aa67e367f9b5503ef8075bb5126`。输入及四份 YAML 见 [configs](configs)。AR 同为 `max_num_seqs=4`、4 GiB 原生 KV 池、24576 context、APC/chunked prefill 关闭、相同 AR Graph 配置。两阶段接收容量 4、声学执行容量 1，按实际长度分配。
- **干净计时**用生产 worker；各 engine 先预热并发四条，再跑单条 1024 帧与三轮并发四条。没有 probe worker、NVTX 或 Nsight。请求计时到最终输出返回；batch 时间包含返回后的轻量输出检查，不含音频 SHA256 计算。两端顺序执行，没有同时占卡。
- **观察运行**是另一对 engine：相同并发四条预热后采集一轮。外置 worker 包装记录 CPU/NVTX、CUDA events、显存快照和 semantic token；Nsight 用 CUDA API correlation ID 关联 kernel 与 NVTX。两个 trace 共 1,388,874 个 kernel，负时长记录为 0。单阶段全部分类；两阶段 24 个小 kernel、合计 44.731 微秒未分类。
- CUDA event 为流上的经过时间，包含等待；kernel interval 时长也可能受资源竞争影响。多个 category 可以重叠，不能直接求和当作 wall time。跨 context 的 kernel 区间重叠不证明 SM 指令在同一时刻执行，更不是 SM 利用率或已消除切换开销的证据。
- 本轮每批恰好 4 条，没有第 5 条 waiting 请求，不能直接测量解除全局 admission 阻塞的收益。接收端四次发布均一次成功，没有 Busy 重试；本轮差距不是接收槽已满导致。

两阶段单请求耗时减少 3.04%（仅一轮），并发 4 中位耗时增加 6.71%，吞吐减少 6.29%。所有计时输出通过有限值、固定长度及 error=0 检查。原始逐请求时间见 [timing-summary.json](evidence/timing-summary.json)、[单阶段](evidence/single-timing/summary.json)和[两阶段](evidence/kv-timing/summary.json)。

### 1. HOLD 是真实工作，已经省掉

单阶段的 698 个 HOLD row 中，465 步与仍在生成 semantic 的行同批，233 步只含 HOLD。后者的 backbone kernel union **1.844 秒**；混合 batch 的成本不能按行数直接拆分。两阶段没有 HOLD row，但新增条件 prefill。因此不能把 698 个 token 等价换算成端到端节省时间。

本轮两阶段整个 AR backbone union 减少约 **1.527 秒**。这些工作原本部分与声学重叠，所以消除后不必然等比例缩短请求完成时间。

### 2. 条件 KV 生成路线不同，transfer 没有消掉条件计算

单阶段在声学 side stream 调用 `CachedNAR._prefill()`，重新用完整 `prefix + semantic + end` 做 dense 条件计算，kernel union 合计 **246.807 ms**。

两阶段仍需要完整条件 prefill，但交给 AR 原生 Qwen/paged KV 路径执行，再传给声学。记录到 8 个 condition rows / 4080 scheduled tokens，包含四次整段 prefill及其收尾步。含条件 row 的 backbone batch kernel union 合计 **390.538 ms**，其中一部分与其它 semantic row 同批，**不能全部归为条件计算，也不能直接与 246.807 ms 作孤立算子比较**。两条路径的最后一层计算和数值实现亦不完全相同。

它当前解决的是让 AR worker 负责条件 KV、声学 worker 无须常驻完整 AR 权重，不是直接复用 semantic decode KV 跳过条件 prefill。没有新 parity 证据前不取消条件 prefill。此前固定相同 KV/噪声的声学精确对照属于 [初版两阶段报告](../2026-10-03-yue2-two-stage/README.md) 的独立证据。

### 3. 拷贝很短，映射释放和同步 ACK 值得单独处理

| 请求帧数 | 整次 publish（CPU） | ACK → take | IPC close API |
|---|---:|---:|---:|
| 512 | 24.274 ms | 14.789 ms | 0.397 ms |
| 768 | 21.985 ms | 11.599 ms | 0.341 ms |
| 1024 | 126.728 ms | 2205.636 ms | 99.240 ms |
| 1280 | 91.722 ms | 3276.394 ms | 71.668 ms |

四次 publish 总计 **264.710 ms**，其中 `_receive_ack` 等最终 ACK 总计 **251.769 ms**；Prepare 等待仅 **1.471 ms**。真实 gather kernel 共 224 个、union **3.049 ms**。其 CUDA event 经过时间为 **45.559 ms**，包含同流等待与 CPU 分批发射间隙，不能误报成纯复制耗时。

Nsight 明确记录四次 `cudaIpcCloseMemHandle` 共 **171.646 ms**，长的两次发生在 receiver 释放 imported references、发送 ACK 之前。源码的 `publish()` 在 AR runner 执行线程同步调用，直到最终 ACK 返回，所以这些停顿会挡住该 worker 的后续执行；它与已经移除的 scheduler 全局 waiting admission gate 是两件事。

接收容量检查时 pending 为 0/0/1/1；四槽没有耗尽。后两次 ACK → take 的秒级等待发生在 **已成功接收之后**，对应声学 worker 还在完成前一首，不能归罪于 gather 慢或没有预分配。

CUDA IPC 映射源 storage 后仍做 GPU gather 成连续 K/V；无 KV 的 CPU 往返，但并非端到端 zero-copy。不能为了优化 ACK 提前复用源 blocks；导入引用/读完成/ACK 生命周期必须继续成立。

### 4. 声学慢在执行区间，AR 提前产出形成后段队列

| 帧数 | 单阶段 NAR CUDA event | 两阶段 NAR CUDA event |
|---|---:|---:|
| 512 | 2.393 s | 3.338 s |
| 768 | 3.752 s | 6.104 s |
| 1024 | 4.472 s | 4.875 s |
| 1280 | 5.890 s | 5.441 s |
| 合计 | **16.507 s** | **19.758 s** |

这不是禁用了上游优化：两端 NAR velocity 的 eager/capture/replay 数完全相同，原 NAR 融合/编译/Graph 路径与单曲串行声学执行保留。单阶段由 `_SynthesisQueue.pump()` 在每个 AR step 推进；两阶段由独立 acoustic worker 调用同一 job 的 `complete()/drain()`。两端代码均创建高优先级声学 stream，但 CPU 推进方式、CUDA context 和 AR/声学资源竞争时序已经改变。

单阶段最后一个 semantic 在 batch 约 17.21 秒完成，两阶段约 15.79 秒完成；两阶段后半段却积累声学队列。本轮最长一首在 AR 已结束后运行，其 NAR 反而较单阶段快，前两首与其它请求 AR 重叠时变慢。**这支持优先检查同卡调度/竞争，而不是继续调大接收容量；尚不构成对某个 CUDA context/priority 机制的唯一因果证明。**

## 显存：权重仅多 4 KiB，不能全部叫 KV 池

probe 完成后同步读取两端 allocator snapshot，按实际 CUDA storage 指针去重参数（含独立加载的 VAE）：

| 项目 | 单阶段 | 两阶段合计 |
|---|---:|---:|
| 参数 storage | 6.916191 GiB | 6.916194 GiB |
| 其中 AR | 4,331,915,264 B | 同左 + 4096 B final norm |
| NAR | 2,818,816,000 B | 相同 |
| latent projections | 9,973,888 B | 相同 |
| VAE | 265,497,864 B | 相同 |
| 请求结束时 allocated | 11.404 GiB | 11.501 GiB |
| 请求结束时 reserved | 18.447 GiB | 19.160 GiB |
| 本次 trace 全设备 NVML 峰值（200 ms 采样） | 19,303 MiB | 20,368 MiB |

两阶段 worker 拆分权重，只有 4096 B final norm 冗余。这个参数统计不将任意非参数运行缓存算作权重。两边仍有相同的 4 GiB 原生 AR KV 池；接收 dense KV 的四次实际分配分别约 125.45/181.56/238.00/293.67 MiB，分配含后续 NAR 的可写位置，并非都同时存活。

结束时 reserved 比 allocated 多的空间主要是分配器保留空间，不能算作当前仍活跃的 KV。两阶段多一个 allocator/context，不能共享整个缓存池。此次 graph-private segment 总大小两边均约 278 MiB；差异主要落在普通 allocator segment，不能笼统归为 Graph 私有池膨胀。NVML 还计入框架 allocator 外的 CUDA/context 等占用，不能用参数+KV 两项强行凑平。

不同 worker 的 peak_allocated 发生时刻可能不同，本报告不把各进程 peak 求和伪装成同一时刻的 GPU 峰值。此次固定长度 workload 的数字也不替代之前自然长曲的显存报告。

## 下一步可以怎样验证

保留两阶段边界，优先做两项针对性干预：

1. 在相同已保存 KV/噪声、相同 NAR shape 下，分别测 acoustic 独跑与 AR 共跑，核对相同 NAR kernel 的耗时及排队变化；然后再区分 context、调度优先级和 CPU pump/drain 方式，不能现在就认定是某一个因素。
2. 将当前同步交接的 export/import/gather/close/ACK 分别测量并缩短 AR worker 停顿。尤其审查长 `cudaIpcCloseMemHandle`，任何缓存映射或异步交接方案都必须先设计清楚源 blocks 与导入引用的生命周期，不能提前 ACK 换取表面性能。

当前不建议根据这批数据恢复固定预分配或单纯增大接收容量：没有发生 Busy，复制 kernel 只有约 3 ms。也没有证据要求放弃两阶段架构。本轮止于 probe，不夹带新的执行逻辑优化。
